# Git & GitHub basics (17:10–17:30)

## Why version control

- Without Git
    - `final_v2_REAL.zip` on someone's laptop
    - Two people edit the same file, one person's changes are lost
    - Nobody knows what changed last Tuesday or why
- Git: every change is a snapshot you can inspect, compare and undo
- GitHub: one shared history online, plus review before code lands on `main`
- Your commit history is part of the score: everyone commits

## The 7 words

- **Repo**: the project folder plus its full history, one per team
- **Commit**: a saved snapshot with a message, e.g. `Add product CRUD page`
- **Branch**: an isolated line of work, named after the feature, e.g. `feature/sales-order`
- **Merge**: combine one branch into another, e.g. feature branch → `main`
- **Remote**: the copy on GitHub, called `origin`
- **Pull request (PR)**: a proposal to merge, with review and discussion
- **Merge conflict**: two branches changed the same lines, you resolve it by hand

## Daily workflow

#### Clone → branch → commit → push → pull request → merge

1. Clone the team repo (once per laptop)
    
    ```bash
    git clone https://github.com/<team>/<repo>.git
    cd <repo>
    ```
    
    - After this you never clone again: you pull
2. Create a branch for every feature
    
    ```bash
    git switch main
    git pull
    git switch -c feature/product-crud
    ```
    
    - Name it after the feature: `feature/product-crud`, `fix/login-redirect`
3. Commit small, often
    
    ```bash
    git status
    git add .
    git commit -m "Add product list and form"
    ```
    
    - Run `git status` before every commit: stop if you see `.env` or `node_modules`
    - One idea per commit, message in the imperative
4. Push the branch
    
    ```bash
    git push -u origin feature/product-crud
    ```
    
    - `-u` only the first time, after that `git push`
5. Open a pull request on GitHub
    - Base: `main`, compare: your branch
    - Write what you did and how to test it
    - Request a reviewer from your team
    - Keep it small: one feature, ideally under 300 lines
6. Merge and update
    - The reviewer approves, merges on GitHub and deletes the branch
    - Everyone updates `main`:
    
    ```bash
    git switch main
    git pull
    ```
    

#### What the history looks like

```
main                  C1 --- C2 ---------------- M --- C3
                               \                /
feature/product-crud            F1 --------- F2
```

- C1: initial commit, C2: README, F1: product list, F2: product form, M: merge commit from the PR
- Branches start from `main` and come back to `main` through a PR
- `main` always works and is always deployable: experiments live on branches

## Resolving a merge conflict

- Example: you added an `sku` column to `schema.sql`, a teammate changed the `price` line
1. Pull `main` into your branch
    
    ```bash
    git switch feature/product-crud
    git pull origin main
    ```
    
    - Git prints `CONFLICT (content): Merge conflict in schema.sql`
2. Open the file: Git wrote both versions between markers
    
    ```sql
    <<<<<<< HEAD
      price numeric(12,2) not null,
      sku text not null unique,
    =======
      price numeric(12,2) not null check (price >= 0),
    >>>>>>> main
    ```
    
    - Above `=======`: your version, below: theirs
3. Decide the final content: yours, theirs or a mix, then delete the marker lines
    
    ```sql
    create table products (
      -- other columns unchanged
      price numeric(12,2) not null check (price >= 0),
      sku text not null unique
    );
    ```
    
4. Commit and push
    
    ```bash
    git add schema.sql
    git commit -m "Resolve conflict in schema.sql"
    git push
    ```
    
    - The pull request updates itself
- Prevention
    - Small PRs
    - Pull `main` every day
    - Split work by module, so two people rarely edit the same file

## Team rules

- One repo per team, every member is a collaborator
- Feature branches only, never commit directly on `main`
- Every change goes through a PR reviewed by a teammate
- Small commits, clear messages, pull `main` every day
- Never commit secrets
    - Put `.env` in `.gitignore` before the first commit
    - Commit `.env.example` with empty values, share real keys privately

## Mini exercise (10 mins)

1. One member creates a repo on GitHub and adds the others as collaborators
2. Everyone clones it and creates a branch `<your-name>/hello`
3. Add one line with your name to `README.md`, commit and push
4. Open a pull request, a teammate reviews and merges it
5. Everyone runs `git switch main` and `git pull`
- Pass: `README.md` on `main` shows every member's name
- Fail: GitHub asks for a password → sign in with `gh auth login` or use a personal access token
- Bonus: two people change the same line and resolve the conflict
- Keep the repo: you may reuse it for the project

# SaaS (17:30–17:45)

## What is SaaS

- Software as a Service: software delivered over the internet, run by the vendor, paid for as a subscription
    - No install: open a browser or app, log in, work
    - The vendor runs hosting, updates, security and backups
    - Pay per user or per month instead of buying a license once
    - Tiers (Free, Pro, Enterprise) unlock features, limits and support
- Examples
    - Google Workspace: per user per month
    - Slack, Notion, Salesforce
    - Shopify: monthly plan plus a fee per sale
    - Odoo Online: ERP in the cloud
- Properties every SaaS has, and your Mini ERP needs
    - Always on: a public HTTPS URL that works from anywhere
    - Multi-user: sign up, log in, invite teammates
        - Use Supabase Auth (email and password), never write your own password hashing
    - Role-based: Admin, Sales, Warehouse, Accountant see and do different things
        - Enforced in the backend, not only by hiding buttons

## Multi-tenancy

- One application, many customers (tenants), and they never see each other's data
    - Siam Bean and a bakery use the same cloud ERP: same code, same servers, separate data
- Database
    - Every business row carries a `company_id`
    - Every query filters by it: forget it on one screen and the bakery sees Siam Bean's prices
- App
    - A user belongs to one company
    - Roles are per company
- Supabase: Row Level Security (RLS) makes the database refuse rows from another company, even if the frontend has a bug
- Why vendors love it: one deployment to run, update and secure for every customer
- Without it: one copy of the app per customer, every bug fixed in every copy
- Project: multi-tenancy is a stretch goal, but add `company_id` to your tables from day one

## SaaS vs on-premise

|  | SaaS | On-premise |
| --- | --- | --- |
| Install | None | On company servers |
| Cost | Monthly subscription (OpEx) | Upfront license plus hardware (CapEx) |
| Updates | Automatic, managed by the vendor | Manual IT projects |
| Customisation | Configuration, apps, APIs | Anything, but every change is expensive to keep through upgrades |
| Data and control | In the vendor's cloud, shared responsibility | Fully in-house |
| Example | Odoo Online, NetSuite | SAP on your own servers |
- Neither is always better
    - Banks and hospitals often need on-premise for regulation
    - A 5-person coffee distributor should never run its own servers
- "I want to own it, not rent it": owning also means owning the server, backups, upgrades and security patches

## Siam Bean Co. today

- Orders arrive by LINE and phone, sales retypes them into a spreadsheet
- Warehouse counts stock in another sheet: always slightly wrong, the two sheets never talk
- Invoices are made in Word and numbered by hand
- The accountant reconciles VAT at the end of every month
- Already rents SaaS: Google Workspace, LINE Official Account, a bank app
- Missing: one system where an order updates stock and creates the invoice → an ERP

# ERP (17:45–18:00)

## What is ERP

- Enterprise Resource Planning: one system that runs the core operations of a business on one shared database
- Modules of one application: Sales, Inventory, Purchasing, Accounting, HR, Dashboard
    - They all read and write the same tables
    - Not six apps exchanging files
- A sale is one event
    - Sales confirms an order → stock updates, an invoice is created, the dashboard updates
    - No retyping
- Examples: SAP, Oracle NetSuite, Microsoft Dynamics, Odoo
- An ERP owns the operational truth: what we have, what we sold, what we are owed, what we owe
    - Marketing email, website analytics, customer chat: separate tools that integrate with the ERP

## Before ERP vs with ERP

- Before: sales in Excel, stock in another file, accounting in another tool
    - Nothing matches, someone reconciles by hand every month
- With ERP: a confirmed sale reduces stock and creates the invoice automatically
    - Fewer errors, real-time numbers, one source of truth
- The real cost is not the software: you must define the process and master data first
    - What exactly is a product?
    - When exactly is an order confirmed?
    - Who is allowed to change a price?
    - ERP projects fail on data and process, not on code
- Everyone must follow the same process
    - e.g. a discount goes through a discount field with a limit, not a lower number typed by hand

## Real ERPs

- **Odoo** (SMEs, open-source core, Odoo Online is the SaaS version)
    - Apps grid: Sales, Inventory, Invoicing
    - Quotation form: customer, order lines, totals
    - **Confirm** → sales order, and a delivery is created in Inventory
    - After delivery: **Create invoice**
- **SAP Business One** (small and mid-size, on-premise or hosted by a partner)
    - Document screens: header (customer, dates) and rows (item, quantity, price)
    - **Copy To** moves Sales Order → Delivery → A/R Invoice
    - Stock lives in Item Master Data, per warehouse
- **ERPNext** (open source, Python, self-hosted or Frappe Cloud)
    - Every record is a DocType with a list view and a form
    - Selling → Sales Order, Stock → Delivery Note, Accounts → Sales Invoice
    - Numbering from a naming series, e.g. `SO-0001`
- One pattern: master data + numbered documents that flow into each other
- The button that turns one document into the next (Confirm, Copy To, Create invoice) is where the business rules live: design it first

## Order-to-cash (O2C): money in

1. Café Lune messages on LINE: "20 kg of Arabica for Friday"
2. Sales creates quotation `QT-0007` and confirms it into sales order `SO-0007`
    - 20 kg reserved, so nobody promises the same beans twice
3. Warehouse validates delivery `DO-0007`
    - Stock on hand −20
4. Invoice `INV-0007` is generated from the order lines
    - 20 kg × 450 THB = 9,000 + 7% VAT 630 = **9,630 THB**
5. Accountant records the bank transfer
    - Receivable cleared
6. Dashboard shows today's sales and open receivables
- All documents are linked: from the invoice you can click back to the order and the delivery
- VAT
    - Store the unit price without VAT on the order line
    - Compute VAT on the invoice, store the VAT amount and the total on the invoice
    - The invoice is a frozen legal document: product prices can change tomorrow without touching it
- Project minimum: sales order → invoice, stock reduced on confirmation (delivery step optional)

## Procure-to-pay (P2P): money out

1. Inventory flags Arabica below its reorder level (50 kg)
2. Purchasing sends purchase order `PO-0003`: 200 kg to the farm in Chiang Rai
    - Sales can see the expected quantity
3. Warehouse receives the goods `GR-0003`
    - Stock +200
    - If only 180 arrived, the 20 kg difference stays open on the PO
4. Supplier bill `BILL-0003` becomes a payable
5. Accountant matches bill to receipt and pays
    - Payable cleared
- O2C and P2P meet in inventory and accounting
    - Stock goes down in one, up in the other
    - Money comes in in one, goes out in the other
    - That is why they share one database
- Project: purchasing is a stretch goal, the minimum is a manual stock-in

## Why ERP matters for an FDE

- FDEs are embedded with clients, and clients run an ERP
    - Integrate with it, build on top of it, pull data out for dashboards, add AI features next to it
- Clients describe problems in business-flow terms, not code
    - "Orders are confirmed but stock does not update"
    - "Invoices go out late"
- Day-one questions you can now ask
    - Which document triggers the stock movement?
    - Who is allowed to confirm?
    - What is your numbering series?

# ERP components (18:00–18:25)

## Module map

| Module | Contains |
| --- | --- |
| Master data | Products, customers, suppliers, employees |
| Inventory | Stock levels, movements in and out, low-stock alerts, warehouses |
| Sales | Quotation → sales order → delivery → invoice |
| Purchasing | Purchase order → goods receipt |
| Accounting | Invoices, payments, receivables, payables, simple P&L |
| HR (optional) | Employees, attendance, payroll |
| Reporting | Sales summary, top products, stock value |
| Cross-cutting | Auth and roles, tenancy, audit log, numbering |
- Master data is the foundation: every document references a product, customer or supplier
- Build order: master data → inventory movements → sales → dashboard
    - Each module depends only on the ones before it
    - Dashboard first = nothing to put on it

## Core modules

#### Master data: the nouns

- Product: SKU, name, unit, cost, sale price, reorder level
    - `ARB-1KG`, Arabica 1 kg, cost 320 THB, price 450 THB, reorder at 50
- Customer: name, tax ID, address, contact, payment terms
    - Café Lune, 30-day credit
    - Tax ID is required on a Thai tax invoice
- Supplier: name, contact, lead time, payment terms
    - Doi Chang Farm, 7-day lead time
- User: name, email, role, company
    - Nok, Sales, Siam Bean
- Rules
    - SKUs are unique
    - Never delete a product that has documents: deactivate it
    - Validate tax IDs and prices
    - Product price = today's price, order line price = price at the moment of sale: two different columns

#### Inventory: every movement is a row

- Stock on hand = sum of movements, never a number you edit by hand
- Stock card `ARB-1KG`

| Date | Document | Quantity | Balance |
| --- | --- | --- | --- |
| 14 Oct | Goods receipt GR-0003 | +200 | 230 |
| 14 Oct | Delivery DO-0005 | −40 | 190 |
| 15 Oct | Delivery DO-0006 | −20 | 170 |
| 15 Oct | Adjustment ADJ-0002 (damaged bags) | −3 | 167 |
- Every movement references a document, a date and a person: a free audit trail
- With a quantity column you can never answer "why is the stock wrong?"
- In: goods receipt, customer return, manual adjustment +
- Out: delivery, write-off, manual adjustment −
- Low-stock alert is a query: on hand below reorder level
- Optional: warehouses, reserved vs available
- Performance: Postgres sums thousands of rows in milliseconds, add a cache only if you ever need it
- Project minimum: stock changes automatically on sales, a manual stock-in exists

#### Sales: quotation → sales order → delivery → invoice

- Quotation: draft, no stock effect (a promise of price, not of stock)
- Sales order: confirmed, reserves or deducts stock
- Delivery: validated, reduces stock
- Invoice: amount due, with 7% VAT
- Every document has the same shape
    - Header: number, date, customer, status, totals
    - Lines: product, quantity, unit price, line total
    - Build it once for the sales order, the invoice is almost a copy
- Status is a state machine: `draft` → `confirmed` → `delivered` → `invoiced` → `paid`, or `cancelled`
    - Cannot confirm if quantity is greater than available stock
    - Cannot edit lines after invoicing
- Project minimum: sales order → invoice, stock reduced on confirmation (quotation and delivery optional)

#### Purchasing: purchase order → goods receipt

- Need (low-stock alert or forecast) → purchase order `PO-0003` → goods receipt `GR-0003` (stock up) → supplier bill `BILL-0003` (payable)
- Same document shape as sales, the partner is a supplier
- Partial receipts are normal: ordered 200, received 180, 20 still open
- Three-way match: PO quantity = received quantity = billed quantity, then pay
- Thai SMEs often buy on 30 or 60-day credit: payables are a list of open items
- Project: stretch goal, and the best one, because it reuses everything from sales

#### Accounting: money follows the documents

- Invoices (money in) and bills (money out) create open items, payments close them
    - Receivables (AR): unpaid invoices
    - Payables (AP): unpaid bills
- Simple P&L

| Line | THB |
| --- | --- |
| Revenue (from invoices) | 412,000 |
| Cost of goods sold | −291,000 |
| **Gross profit** | **121,000** |
| Expenses (rent, salaries, delivery) | −86,000 |
| **Net profit** | **35,000** |
- Thailand
    - 7% VAT on invoices
    - Tax ID on documents
    - Withholding tax when buying services: know it exists, no need to build it
- Project: invoice + payment status is enough
    - P&L is a bonus: save the cost on the order line next to the price, so old margins never change

#### Reporting & dashboard: the owner's view

- Required: at least 3 metrics, computed live from the same tables

| Tile | Example | Query |
| --- | --- | --- |
| Sales today | 12,450 THB | SUM of invoice totals dated today |
| Low-stock products | 4 | COUNT of products with on hand below reorder level |
| Open invoices | 7 · 58,300 THB | COUNT and SUM of invoices not paid |
| Stock value | 91,200 THB | SUM of on hand × cost |
- Not hard-coded, not cached somewhere else: the grader creates an order and then checks the dashboard
- Correctness before charts: a wrong number on a nice chart is worse than a right number in plain text
- Pick the metrics the owner needs: did we sell, are we running out, who owes us, what is our stock worth

## Cross-cutting capabilities

#### Authentication and roles

| Screen or action | Admin | Sales | Warehouse | Accountant |
| --- | --- | --- | --- | --- |
| Products and customers | Edit | Edit | View | View |
| Create and confirm sales orders | Yes | Yes | – | – |
| Stock in, out, adjust | Yes | – | Yes | – |
| Invoices and payments | Yes | View | – | Yes |
| Dashboard | Yes | Yes | Yes | Yes |
| Users and settings | Yes | – | – | – |
- At least 2 roles, enforced in the backend, not only by hiding buttons
    - Hidden button + working API = decoration, not roles
    - Supabase: RLS policies, or role checks in FastAPI
- The matrix is your test plan: log in as each role and try each row
- Test: log in as Warehouse, call the confirm-order endpoint directly
    - Pass: `403`
    - Fail: the order is confirmed

#### Tenancy, audit, numbering, import / export, validation

- Multi-tenant: `company_id` on every table + RLS (stretch, but add the column now)
- Audit log
    - Full version: a table of events
    - Starter version: `created_by` and `updated_at` on every table, from day one
- Document numbering: `SO-0001`, `INV-0001`
    - Sequential per company, never reused, never edited
    - Generated in the backend inside a transaction, so two users never get the same number
- Search, filter, pagination on every list screen
- CSV import and export: nobody types 300 products, accountants work in Excel
- Validation everywhere: price ≥ 0, quantity > 0, unique SKU, required tax ID
- Only time for two? Numbering and validation

## The whole flow, end to end

1. Customer orders
2. Sales order created and confirmed
3. Stock deducted
4. Invoice issued
5. Payment recorded
6. Dashboard updated
- One action in Sales touches Inventory, Accounting and Reporting
- This flow working end to end is worth 7 of the 20 project points
- Test story: "Café Lune orders 20 kg"
    - Create the customer, the product with stock, the order
    - Confirm, watch stock drop, open the invoice, record the payment, check the dashboard
    - Pass: the numbers agree on every screen
    - Fail: any screen disagrees → that is your next bug

# Understanding business requirements (18:25–18:45)

## What a business owner actually needs

- Owners talk in problems, not software
    - "I lose track of stock"
    - "Invoices take forever"
    - "I never know who still owes me money"
    - Collect these sentences exactly as spoken
- They want outcomes: fewer mistakes, less paperwork, money arriving sooner, a clear picture of the business
    - A feature that produces none of these is not a requirement
- They know the process by heart but have never written it down
    - Write it down with them: the gaps appear, e.g. "who sets the price for a new customer?"
- They are busy
    - Prepare your questions
    - Listen more than you talk
    - Do not pitch your solution in the first meeting
- A requirement is a sentence the owner agrees with, not a feature you find exciting

## How to interview a user

| Topic | Sample question | Listen for |
| --- | --- | --- |
| Their day | "Walk me through what happens when a customer orders." | Steps, documents, who does what → your flow of screens |
| Pain points | "What goes wrong most often? What costs you the most time?" | Problems worth solving first |
| Current tools | "Where do you keep that today? Can I see it?" | Spreadsheet columns → your first data model |
| Numbers | "How many products, customers, orders per day?" | Scale: search, pagination, speed |
| People | "Who else touches this? What must they not see?" | Roles and permissions |
| Rules | "When is an order final? Can a price change afterwards?" | Statuses, validation, business rules |
| Priorities | "If we could fix only one thing by next week, which one?" | Your must-have list |
- Habits
    - Ask "why?" at least twice: the first answer is usually a symptom
    - Write down their words, not your solution
    - Always ask to see the spreadsheet, chat or notebook: photograph it
    - Sketch the current process together with boxes and arrows
    - Finish by repeating the process back: "Did I understand this right?"

## Pain point → requirement → feature → user story

1. **Pain point**: the problem in the owner's words
    - "Stock in the sheet is always wrong"
    - A symptom, not yet something to build
2. **Requirement**: what the system must do, in a testable sentence
    - "Stock must update automatically when an order is confirmed"
    - Shape: the system must + an observable behaviour
3. **Feature**: the concrete thing you build
    - A Confirm order action that creates stock movements
    - A screen, a button or a rule
4. **User story**: the requirement from the user's chair, with acceptance criteria
    
    ```
    As a warehouse staff, I want stock to update on confirmed orders so that the count is never wrong.
    
    Given 170 kg of ARB-1KG on hand
    When a sales order for 20 kg is confirmed
    Then on hand shows 150 kg
    ```
    
- 1 pain point → 1 to 3 requirements, 1 requirement → about 1 feature
- Write the story before you code: if you cannot write the acceptance criterion, you do not understand the requirement yet

## Functional vs non-functional requirements

| Functional: what the system does | Non-functional: how well it does it |
| --- | --- |
| Create a sales order with lines and confirm it | Speed: product search answers within 1 second for 500 products |
| Reduce stock when an order is confirmed | Security: passwords never stored in plain text, roles enforced in the backend |
| Generate invoice INV-000x from the order with 7% VAT | Availability: public HTTPS URL that works on a phone |
| Only Admin can change a product price | Usability: a new staff member creates an order without training |
| Show low-stock products on the dashboard | Reliability: confirming updates stock and creates the invoice together, or not at all |
- Owners rarely state non-functional requirements, they assume them: ask how fast, how many users, what if the internet drops
- How to test
    - Functional: do the action, check the result
    - Non-functional: measure a number or check a condition, e.g. a stopwatch, or call the API as the wrong role and expect `403`
- Write at least 2 non-functional requirements for your project, with numbers

## Worked example: Siam Bean Co.

| Pain point | Requirement | Feature | User story | Acceptance criterion |
| --- | --- | --- | --- | --- |
| "Stock in the sheet is always wrong." | Stock must change automatically when goods go out or come in | Confirm order creates a negative movement, a stock-in form creates a positive one | As a warehouse staff, I want stock to update on confirmed orders so that the count is never wrong | Given 170 kg on hand, when SO-0007 for 20 kg is confirmed, then on hand shows 150 kg |
| "Each invoice takes me an hour and the numbers get mixed up." | The system must create a numbered invoice from the order, with 7% VAT | Generate INV-000x from the order lines with sequential numbering | As a sales staff, I want an invoice created from the order so that I never retype it | Given SO-0007 is confirmed, when I click Create invoice, then INV-0007 shows 9,000 + 630 VAT = 9,630 THB |
| "I never know who still owes me money." | The system must list unpaid invoices and the total owed | Open-receivables list and a dashboard tile | As the owner, I want to see unpaid invoices so that I can chase them | Given 7 open invoices, when I open the dashboard, then I see 7 open, 58,300 THB |
- Every story: a role, an action, a benefit, and a Given / When / Then with real numbers
- Real numbers catch real bugs

## Requirements checklist per ERP module

| Module | Ask the owner | Write down (minimum to start building) |
| --- | --- | --- |
| Master data | What do you sell? Who buys it? Who supplies you? | Product (SKU, name, unit, cost, price), customer (name, tax ID, payment terms), supplier |
| Inventory | How do you know how much is left? When do you reorder? | Stock = sum of movements, a manual stock-in, a reorder level per product for the low-stock alert |
| Sales | What does an order look like? When is it final? | Order with lines, Confirm reserves or deducts stock, no confirm without stock |
| Invoicing and accounting | How do you bill? Who pays late? | Invoice from the order, 7% VAT, sequential number, payment marks it paid |
| Purchasing (optional) | How do you buy stock, from whom, how often? | Purchase order and goods receipt that adds stock |
| Reporting | Which three numbers do you check every day? | 3 live dashboard metrics |
| Users and roles | Who uses it? Who must not see money? | At least 2 roles, enforced in the backend |
- One sentence per cell is enough to start
- If a row does not apply to your business, write why
    - e.g. a bubble-tea shop has ingredients instead of bags, but the rows are the same

## Common beginner mistakes

| Mistake | Fix |
| --- | --- |
| Asking "what features do you want?" → a wish list copied from other apps | Ask about problems and the daily routine, then propose features yourself |
| Developer stories: "As a developer, I want a products table" | Write from the user's chair: "As a sales staff, I want to find a product by name so that I can add it to an order in 5 seconds" |
| Vague words: "fast", "user-friendly", "secure" | Give a number or a test: "search answers within 1 second for 500 products" |
| Never looking at the spreadsheet | Photograph it: its columns are your first data model, its messy rows are your edge cases |
| Gold-plating: a chatbot before the invoice works | Thin slice first: order → stock → invoice end to end, then extras |
| Everyone can edit everything | Draw the permission matrix before the screens |

# The Project: Mini ERP (18:45–19:10)

## Stack

**Recommend:** The CU FDE2 stack

- Database: Supabase (Postgres + Auth + RLS)
- Backend: Python FastAPI with `uv`
- Frontend: React TypeScript with Vite
- Deploy: Cloudflare Workers, or Google Cloud Run for the backend
- Set up with the manuals in [‣](https://app.notion.com/p/3f1bcb52c6278097adf8c8a02968680d?pvs=21): only what is new for the ERP is below

**Alternative:** Supabase as the whole backend (Auth + Postgres + RLS + database functions) with React or Next.js, deployed on Vercel or Cloudflare

- Any stack you know well is fine, as long as the database is relational and the app is deployed
- Do not learn a new framework this week

#### Architecture

```
Browser (React TS)  -->  Backend (FastAPI or Supabase)  -->  Postgres (Supabase)
UI, forms, dashboard     business rules + role checks       schema from your ER diagram + RLS
```

- Keep business rules in one place
    - "Confirm order" reduces stock and creates the invoice in one transaction, in the API or a Postgres function
    - Never three separate calls from the frontend: one day the second call fails and stock is wrong forever
- Keys in environment variables: commit `.env.example`, never `.env`

## ER diagram (starting point)

- Starting point for Siam Bean: let `/grill-with-docs` confirm it, add columns only if the scenario needs them

| Table | Columns |
| --- | --- |
| companies | id, name, tax_id (the tenant) |
| users | id, company_id, email, role |
| customers | id, company_id, name, tax_id |
| products | id, company_id, sku, name, price, cost, reorder_level |
| stock_movements | id, product_id, quantity (+ or −), ref_doc, created_at |
| sales_orders | id, number (SO-0001), customer_id, status, date, created_by |
| order_items | id, order_id, product_id, quantity, unit_price |
| invoices | id, number (INV-0001), order_id, total, vat, status, due_date |
| payments | id, invoice_id, amount, paid_at |
- Relations (one → many)
    - companies → users, customers, products
    - customers → sales_orders
    - sales_orders → order_items, products → order_items: `order_items` splits the many-to-many between orders and products
    - products → stock_movements
    - invoices → payments
    - sales_orders → invoices: one-to-one in the minimum version
- Design notes
    - Every business table carries `company_id`: ready for multi-tenancy
    - No quantity column on products: stock on hand = sum of `stock_movements` per product
    - `unit_price` (and `unit_cost` for a P&L) are copied onto the order item, because prices change and old orders must not
    - The invoice stores its own total and VAT for the same reason
    - `created_by` is your audit trail: add it to invoices and movements too

#### Starter schema (Supabase SQL Editor)

```sql
create table companies (
  id bigint generated always as identity primary key,
  name text not null,
  tax_id text
);

create table users (
  id uuid primary key references auth.users (id),
  company_id bigint not null references companies (id),
  email text not null,
  role text not null check (role in ('admin', 'sales', 'warehouse', 'accountant'))
);

create table customers (
  id bigint generated always as identity primary key,
  company_id bigint not null references companies (id),
  name text not null,
  tax_id text,
  active boolean not null default true
);

create table products (
  id bigint generated always as identity primary key,
  company_id bigint not null references companies (id),
  sku text not null,
  name text not null,
  unit text not null default 'pcs',
  price numeric(12,2) not null check (price >= 0),
  cost numeric(12,2) not null check (cost >= 0),
  reorder_level integer not null default 0,
  active boolean not null default true,
  unique (company_id, sku)
);

create table stock_movements (
  id bigint generated always as identity primary key,
  company_id bigint not null references companies (id),
  product_id bigint not null references products (id),
  quantity integer not null check (quantity <> 0),
  ref_doc text not null,
  created_by uuid references users (id),
  created_at timestamptz not null default now()
);

create table sales_orders (
  id bigint generated always as identity primary key,
  company_id bigint not null references companies (id),
  number text not null,
  customer_id bigint not null references customers (id),
  status text not null default 'draft'
    check (status in ('draft', 'confirmed', 'delivered', 'invoiced', 'paid', 'cancelled')),
  order_date date not null default current_date,
  created_by uuid references users (id),
  unique (company_id, number)
);

create table order_items (
  id bigint generated always as identity primary key,
  order_id bigint not null references sales_orders (id) on delete cascade,
  product_id bigint not null references products (id),
  quantity integer not null check (quantity > 0),
  unit_price numeric(12,2) not null check (unit_price >= 0),
  unit_cost numeric(12,2) not null check (unit_cost >= 0)
);

create table invoices (
  id bigint generated always as identity primary key,
  company_id bigint not null references companies (id),
  number text not null,
  order_id bigint not null unique references sales_orders (id),
  subtotal numeric(12,2) not null,
  vat numeric(12,2) not null,
  total numeric(12,2) not null,
  status text not null default 'open' check (status in ('open', 'paid', 'cancelled')),
  due_date date,
  created_at timestamptz not null default now(),
  unique (company_id, number)
);

create table payments (
  id bigint generated always as identity primary key,
  invoice_id bigint not null references invoices (id),
  amount numeric(12,2) not null check (amount > 0),
  paid_at timestamptz not null default now()
);

create view stock_on_hand as
select p.id as product_id, p.company_id, p.sku, p.name, p.reorder_level,
       coalesce(sum(m.quantity), 0) as on_hand
from products p
left join stock_movements m on m.product_id = p.id
group by p.id;

alter table companies enable row level security;
alter table users enable row level security;
alter table customers enable row level security;
alter table products enable row level security;
alter table stock_movements enable row level security;
alter table sales_orders enable row level security;
alter table order_items enable row level security;
alter table invoices enable row level security;
alter table payments enable row level security;
```

- With the CU FDE2 setup (only FastAPI talks to the database with the secret key), RLS on with no policy is fine
- If the frontend calls Supabase directly, add a policy per table first

## Build the core flow (Claude Code + Matt Pocock skills)

- Same change request workflow as CU FDE2: one module = one branch = one pass through the flow
- Flow: new branch → `/grill-with-docs` → `/to-spec` → `/to-tickets` → `/tdd` → `/implement`
- Example below: **Confirm order → stock → invoice** (the 7-point flow)
1. Prepare the repo and database (once)
    - Team repo from the Git exercise, with `backend` and `frontend` folders (CU FDE2 manuals 1–3)
    - Run the starter schema in the Supabase **SQL Editor**
    - Insert test data: 1 company, 2 customers, 3 products, a positive stock movement per product
2. Split a new branch
    
    ```bash
    git switch main
    git pull
    git switch -c feature/confirm-order
    ```
    
3. Gather context with `/grill-with-docs`
    - Prompt for Claude Code:
    
    ```
    /grill-with-docs I want a "confirm order" action for our Mini ERP. Confirming a draft sales order must, in one database transaction: check every line has enough stock on hand, create one negative stock movement per line, set the order status to confirmed, and create an invoice with the next INV number for the company, with subtotal, 7% VAT and total. If any line has too little stock, nothing changes and the API returns 409 with a clear message. Only admin and sales may confirm, other roles get 403.
    ```
    
    - Typical questions
        - Transaction in a Postgres function called with `rpc`, or in FastAPI?
        - How is the next number generated so two users never get the same one?
        - How does FastAPI know the user's role and company on each request?
4. Spec and tickets
    - Run `/to-spec`, read the whole spec and fix what is wrong
    - Run `/to-tickets`: e.g. stock check → movements → invoice numbering → role check → UI button
5. Tests first with `/tdd`
    - Prompt for Claude Code:
    
    ```
    /tdd Work on ticket 1. Write failing tests first: confirming an order for 20 kg with 170 kg on hand leaves 150 kg on hand, an invoice INV-000x is created with 9,000 subtotal, 630 VAT and 9,630 total, confirming with too little stock returns 409 and changes nothing, and a warehouse user gets 403. Run them with uv run pytest, show me that they fail, then stop.
    ```
    
    - Red must be seen before green
6. Implement
    - Prompt for Claude Code:
    
    ```
    /implement ticket 1. Make the failing tests pass without changing the tests.
    ```
    
    - Repeat steps 5 and 6 for every ticket, commit after each one
7. Check and merge
    - Pass: in the browser, confirm an order → stock drops on the product list, the invoice opens with the right total, the dashboard updates
    - Pass: as Warehouse, calling the confirm endpoint returns `403`
    - Fail: stock changed but no invoice (or the reverse) → the steps are not in one transaction
    - Open a PR, a teammate reviews, merge into `main`, redeploy

## User stories (given in the scenario)

- **US-1** As a sales staff, I want to create a sales order for a café so that stock is reserved and an invoice can be issued
    - Given products with stock, when I confirm an order, then stock decreases by the ordered quantity and invoice INV-000x is created with the same lines and total
    - Given a line quantity greater than available stock, when I confirm, then I see an error and nothing changes
- **US-2** As a warehouse staff, I want to see which products are low on stock so that I can reorder in time
    - Given a product below its reorder level, when I open the product list, then it shows a low-stock badge and the dashboard low-stock count includes it
- **US-3** As the owner, I want to invite a user with a role so that they only see what they are allowed to
    - Given a Sales user, when they open the Accounting screen, then they get an access-denied page and the API returns `403`
    - Given an Admin, when they open the same screen, then it loads
- **US-4** As an accountant, I want to record a payment against an invoice so that I know what is still owed
    - Given an open invoice, when I record a full payment, then its status becomes Paid and open receivables on the dashboard decrease by that amount
- **US-5** As a sales staff, I want to search customers so that I find one quickly
    - Given 200 customers, when I type part of a name, then the list filters within 1 second and shows at most 20 rows per page
- These are fixed: do not rewrite them, build them. The worksheet versions add Siam Bean numbers (e.g. 170 → 150 kg, 9,630 THB)
